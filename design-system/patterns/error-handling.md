# Pattern: Error Handling

## ใช้เมื่อไหร่
ทุกจุดที่ action อาจล้มเหลวได้ (บันทึกข้อมูล, ค้นหา, ส่ง order) ต้องออกแบบ error state ไว้ล่วงหน้า ไม่ใช่แค่ happy path

## ประเภท Error และวิธีจัดการ

| ประเภท | ตัวอย่าง | วิธีแสดงผล |
|---|---|---|
| **Field-level validation** | กรอกเลขบัตรประชาชนไม่ครบ | Error text ใต้ field ทันที (ดู `form-controls.html` `.field--error`) |
| **Action failure** | กดบันทึกแล้วล้มเหลว (mock ว่า "server" ตอบ error) | `notification-toast.html` (type error) + คงข้อมูลที่กรอกไว้ ไม่ล้างฟอร์ม |
| **Page-level load failure** | โหลดรายการผู้ป่วยไม่สำเร็จ | ข้อความ error กลางหน้าจอ + ปุ่ม "ลองใหม่" (retry) |
| **Not found** | ค้นหาผู้ป่วย/รายการไม่เจอ | Empty state พร้อมคำแนะนำ ไม่ใช่ error (คนละความหมายกับ error จริง) |

## กฎการใช้งาน
- ข้อความ error ต้องบอก**สิ่งที่ผิดพลาด**และ**วิธีแก้**เสมอ ห้ามขึ้นแค่ "เกิดข้อผิดพลาด" ลอย ๆ
- ห้ามใช้คำขอโทษเยิ่นเย้อหรือคำคลุมเครือ ให้ตรงประเด็น เช่น "บันทึกไม่สำเร็จ เชื่อมต่อขาดหาย กรุณาลองใหม่" ไม่ใช่ "ขออภัยในความไม่สะดวก มีบางอย่างผิดพลาด"
- Error ที่เกี่ยวกับความปลอดภัยผู้ป่วย (เช่น บันทึก vitals ไม่สำเร็จระหว่างเคส critical) ต้องเด่นกว่า error ทั่วไป — พิจารณาใช้ `alert-banner.html` แทน toast ธรรมดา
- ทุก mockup ที่มีการดึง/บันทึกข้อมูล ต้อง demo error state ได้อย่างน้อย 1 ทาง (เช่น ปุ่ม "จำลอง error" ซ่อนไว้ หรือ mock ให้ record บางตัวคืน error เสมอ)
