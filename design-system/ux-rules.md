# UX Rules — Gorilla HIS

กติกาเรื่อง**พฤติกรรมและการโต้ตอบ** ของ UI (แยกจาก `design-rules.md` ที่เป็นเรื่อง**หน้าตา/ภาพ**) — ทั้งสองไฟล์ต้องอ่านคู่กันเสมอ ตามลำดับใน `AI_INSTRUCTIONS.md`

## 1. Core UX Principles

1. **แสดงให้ชัดว่ากำลังทำงานกับใคร/อะไรอยู่** — ผู้ป่วยรายไหน, order ไหน, ต้องเห็นตลอดเวลาที่ทำงานในบริบทนั้น (ดู `patient-banner.html`)
2. **แสดง task/state ปัจจุบันเสมอ** — ผู้ใช้ต้องรู้ว่าตอนนี้อยู่ขั้นตอนไหนของงาน
3. **ทำให้ action ถัดไปชัดเจน** — ไม่ต้องเดาว่าต้องกดอะไรต่อ
4. **รักษาบริบทผู้ป่วยที่สำคัญให้มองเห็นตลอด** ในงาน clinical workflow (เช่น แพ้ยา ต้องเห็นแม้เลื่อนหน้าจอ)
5. **ลดการนำทาง/กรอกข้อมูลซ้ำซ้อนที่ไม่จำเป็น** — ถ้าระบบรู้ข้อมูลอยู่แล้ว (เช่น HN ที่เลือกไว้) ห้ามให้กรอกซ้ำ

## 2. Actions

- แต่ละหน้าจอ/บริบท ควรมี **primary action เดียวที่ชัดเจน** (ปุ่มเด่นสุด)
- Secondary action ต้องดูรองลงมาเสมอ (ใช้ `.btn--secondary` ไม่ใช่ `.btn--primary`)
- **Destructive action ต้องมีการยืนยันซ้ำ** ผ่าน `modal-dialog.html` ก่อนทำจริงทุกครั้ง (ยกเลิกนัด, ลบข้อมูล, ยกเลิก order)

## 3. Worklist / รายการงาน

- ช่องค้นหาต้องหาเจอง่าย ไม่ซ่อนอยู่ลึก (ดู `patient-search-bar.html`)
- ตัวกรอง (filter) ต้องมองเห็น/ค้นพบได้ทันที ไม่ต้องกดเปิดหลายชั้น
- สถานะและลำดับความสำคัญ (priority) ต้องชัดเจนด้วย `status-badges.html`
- เมื่อกดเข้าไปดูรายละเอียดจาก worklist แล้วย้อนกลับ ต้องรักษาบริบทเดิมไว้ (ตำแหน่ง scroll, filter ที่เลือก) เท่าที่ทำได้
- ใช้ `worklist.html` เป็นต้นแบบสำหรับคิวงาน/รายการที่ต้องดำเนินการต่อ (ต่างจาก `lab-result-table.html` ที่เป็นตารางแสดงผลอย่างเดียว ไม่ใช่คิวงาน)

## 4. Detail Pattern — เมื่อไหร่ใช้ Drawer/Modal vs เต็มหน้า

| ใช้ | เมื่อไหร่ | Component |
|---|---|---|
| **Drawer** (แผงเลื่อนจากขอบจอ) | งานสั้น ๆ ที่มีบริบทเดียว ไม่ต้องออกจากหน้าหลัก | `drawer.html` |
| **Modal** | ยืนยัน action หรือฟอร์มสั้นมาก (1-2 field) | `modal-dialog.html` |
| **เต็มหน้า (full page)** | Workflow ซับซ้อนหลายขั้นตอน | pattern `form-wizard.md` |

## 5. States ที่ต้องออกแบบครบ

ทุกหน้าจอ/component ที่มีข้อมูลพลวัต ต้องพิจารณา 6 state นี้ (เพิ่มจากเดิม 4 state ใน design-rules — เพิ่ม Success และ Disabled อย่างชัดเจน):

| State | ตัวอย่าง |
|---|---|
| Normal | หน้าจอทำงานปกติ |
| Loading | กำลังดึงข้อมูล |
| Empty | ไม่มีข้อมูลให้แสดง |
| Error | ดึง/บันทึกข้อมูลล้มเหลว |
| Success | บันทึก/ดำเนินการสำเร็จ (ใช้ `notification-toast.html`) |
| Disabled | Action ที่กดไม่ได้ในบริบทนี้ (ต้องมี visual + เหตุผลเมื่อ hover/focus ถ้าเป็นไปได้) |

## 6. Consistency

**ใช้ pattern ที่ approve แล้วซ้ำ ถ้าแก้ปัญหาแบบเดียวกันได้** — ห้ามออกแบบวิธีแก้ปัญหาใหม่สำหรับปัญหาที่มี pattern อยู่แล้วใน `patterns/` หรือ `approved-mockups/` เพียงเพราะอยากลองอะไรใหม่ ๆ ความสม่ำเสมอสำคัญกว่าความคิดสร้างสรรค์ส่วนบุคคล (ดู `design-rules.md` § 1)
